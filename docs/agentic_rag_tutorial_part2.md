# 第四部分　关键代码逐段拆解（可对照源码阅读）

## 4.1 结构化输出兜底：Agent 不崩的地基

```
# app/core/agent_nodes.py：所有决策节点共用的“结构化调用 + 兜底”
async def _json_call(self, *, node, system, user, schema, fallback, state=None):
    for attempt in range(2):                                  # ① 重试一次
        resp = await llm.ainvoke([SystemMessage(system), HumanMessage(user)])
        text = resp.content if isinstance(resp.content, str) else str(resp.content)
        self.stats.record(task=f"agent:{node}", ...)           # ② 逐节点记账
        obj = parse_json_loose(text)                           # ③ 容错解析
        if obj is not None:
            try:
                return schema.model_validate(obj), {"ok": True}
            except ValidationError as e:
                last_err = f"字段校验失败：{e.errors()[:2]}"
        else:
            last_err = "输出不是合法 JSON"
    return fallback, {"ok": False, "reason": last_err}         # ④ 永远返回一个合法决策
```

四个细节各有原因：

- **重试一次**：第一次失败往往是偶发的格式问题，重试成本很低，收益却明显。
- **容错解析**（`parse_json_loose`）：模型可能套上 json 代码围栏、加“好的，这是结果：”、末尾多写一段解释，正则抠出第一个 JSON 对象比要求模型“守规矩”更可靠。
- **字段校验**：Pydantic 校验能拦住“字段名写错、枚举值乱填”这类问题，把它们变成可兜底的失败而不是脏数据。
- **保守兜底**：失败时返回安全默认值（判定 → 不足、校验 → 放行、压缩 → 原文截断）。

> [tip] 这套“重试 + 容错解析 + 字段校验 + 保守兜底”是 LLM 工程里最通用的防御式写法，任何需要解析模型输出的地方都能直接套用。

## 4.2 证据池：去重、打分、按预算裁剪

```
@dataclass
class GradedChunk:
    chunk_id: str; doc_id: str; doc_title: str; page: int | None
    text: str; score: float; stage: str
    relevant: bool = True          # 判定结果：能不能进上下文
    reason: str = ""               # 判定理由（调试时非常有用）
    compressed: str = ""           # 压缩后正文

    @property
    def body(self) -> str:         # 生成时用哪份文本：压缩过就用压缩版
        return self.compressed or self.text

    def to_evidence(self, cite_index: int) -> dict:
        """转成对外返回的证据项（cite_index 与回答里的 [n] 严格对齐）"""
```

- 去重按 `chunk_id`：同一片段被向量与 BM25 同时召回时只保留最高分那条。
- 判定结果与证据存在一起：既是过滤依据，也是给用户看的“为什么用了这条”。
- 压缩与原文分离：兼顾省 token 与可审计。

## 4.3 提示词工程：控制流提示词与回答提示词是两类东西

| 类型 | 例子 | 设计要点 | 失败后果 |
| --- | --- | --- | --- |
| 控制流提示词 | plan / grade / verify / compress / memo | 必须输出 JSON；字段名与取值枚举写死；判定原则要可执行 | 解析失败 → 走兜底，效果打折 |
| 回答提示词 | answer | 身份 + 任务 + 铁律（只用资料）+ 引用格式 + 不知道就说不知道 | 编造、引用错位 |

> [warn] 控制流提示词**不要**写“请尽量”“如果可以”这类模糊表述 —— 它们必须产出机器可判定的结果。判定原则要写成可执行的规则，例如“资料只是话题相近但答不了具体问题 → sufficient=false”。

## 4.4 引擎侧接入：组合而非继承

```
# app/core/engine.py（构造函数里注入，而不是让 engine 继承一堆东西）
self.agent_nodes = AgentNodes(settings, self.router, self.stats)   # 决策层
self.agent = AgentOrchestrator(self)                               # 控制流层

# 对外：与 answer() 同构，方便替换、对比与灰度

```

> [tip] “组合优于继承”在这里不是教条，而是为了**防止 engine.py 变成上帝类**：engine 管知识与检索，agent_nodes 管决策，agent 管控制流，token_stats 管计量。职责单一，才能分别单测。

# 第六部分　值得注意的地方与避坑清单

下面每一条都是改造过程中真实踩到（或差点踩到）的坑，按“现象 → 原因 → 对策”给出。

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| Agent 每问都跑满 3 轮，延迟翻倍 | LLM 判定器天然偏严，几乎总说“不足” | 强证据提前收束（top_score 阈值）+ 首轮只打一条检索式 |
| 判定器说“够”却一条编号都没给 | 模型输出不稳定 | 保守全留（宁可多留不可错杀），并记录兜底原因 |
| 模型输出带代码围栏导致解析失败 | 模型习惯性美化输出 | parse_json_loose：去围栏 + 正则取第一个 JSON 对象 |
| 校验器把正常回答全判成不可信 | 校验提示词过严 / 校验器故障 | 故障时默认放行；提示词明确“过渡语不算编造” |
| 证据为空时模型开始编 | 让模型在无资料时空转是幻觉率最高的场景 | 控制流短路：不调模型，返回确定性拒答模板 |
| 多轮追问的指代丢失 | 检索式里只有“它”“这个” | 规划 / 改写阶段带上历史，产出独立检索式 |
| 上下文超预算被硬截断，句子被砍半 | 简单按字符切割 | 按分数排序整段装，装不下整段丢弃并标注原因 |
| 决策类问题答成散文，没有可执行结论 | 用问答提示词处理决策问题 | 先产出结构化 DecisionMemo，再据此组织自然语言 |
| 成本上去了却说不清贵在哪 | 只有一个总 token 数 | 逐节点 task 记账，by_step 直接看出各步花多少 |
| 改造把老链路改坏 | 新旧代码交织 | 新能力走新类 / 新方法，老接口只加一个开关分支 |
| 评测集全是简单题，改造前后没差异 | 评测集设计不合理 | 补跨段综合 / 同义改写 / 幻觉探针三类题；期望文档只有一篇时下沉到内容层指标 |
| **规划器把问题分类错**（如把"QPS 峰值"判成"问知识库自身"） | LLM 分类会误判，而某些分支走确定性工具、连模型都不调 | 给"抄近路"的分支加确定性口径守卫（见 6.2 坑一） |
| **判定器把高分证据误杀** | LLM 按"单条能否回答"裁，多跳问题需要多条拼起来 | 分数下限保护 + 分情况下限（见 6.2 坑二） |
| **节点输出格式不守约**（该给对象却给数组） | 模型输出不稳定 | 解析器兼容 + 提示词写死形状；兜底保证流程不崩（见 6.2 坑三） |

## 6.2 三个真实踩坑复盘（建议精读）

下面三条不是"假设可能发生"，而是本项目在**真正跑评测时被指标抓出来**的问题。
它们共同说明一件事：**Agent 的错误往往不表现为报错，而表现为"自信地答非所问"**，
所以评测脚本比调试日志更重要。

### 坑一：规划器的分类误判 → 答非所问（幻觉率反而升高）

**现象**：库里没有答案的探针题"你们这套问答系统每天的调用量和线上 QPS 峰值是多少？"
在朴素 RAG 下会正确拒答，改成 Agent 后却变成"知识库当前共有 4 篇文档、72 个分块……"。
评测指标上表现为：**无答案误答率 0% → 40%、幻觉率 0% → 11.1%**。

**根因**：规划器把这个问题判成了 `stats`（问知识库自身情况）类型，
而 `stats` 分支为了省钱走的是**确定性工具** `kb_stats`：直接输出文档数/分块数/后端类型，
**一次大模型调用都没有**（轨迹里只有 1 次调用、13 秒就返回）。
从系统视角看它"完美执行了计划"，从用户视角看它是**答非所问**。

**修复**：给规划结果加一条**确定性的口径守卫**（`_looks_like_kb_self_question`）：

```
# app/core/agent.py：规划结果的口径守卫
_KB_SELF_HINTS = ("知识库", "文档库", "库里", "收录", "有哪些文档", "多少文档",
                  "文档数量", "分块", "索引", "入库", "向量库", ...)

def _looks_like_kb_self_question(question: str) -> bool:
    q = question.lower()
    if not any(h in q for h in _KB_SELF_HINTS):
        return False
    # 故障/性能/容量类问题必须走检索（资料里可能有降级方案），不能走统计
    trouble = ("挂了", "故障", "宕机", "不可用", "qps", "并发", "峰值", "延迟", "耗时",
               "压力", "容量", "负载", "超时", "限流", "崩", "失败")
    return not any(t in q for t in trouble)

if state.task_type == "stats" and not _looks_like_kb_self_question(question):
    guard_note = "规划器判为 stats，但问题并非在问知识库自身 → 守卫改为普通问答"
    state.task_type = "qa"          # 退化为正常检索 + 必要时拒答
    state.reflections.append(guard_note)
```

> [key] **这是"受控 Agent"最有价值的一课**：把决策交给 LLM 没问题，
> 但每个"抄近路"的分支（这里是为省钱用的确定性工具）都必须配一条**确定性守卫**。
> 近路走错时的代价，往往比"多花一次模型调用"大得多。

### 坑二：判定器误杀高分证据 → 回答缺要点

**现象**：评测的"证据要点覆盖率"显示 Agent 比朴素 RAG 低，
逐题对比发现某题检索到 1921 字的证据（含关键词），经过判定过滤后只剩 459 字，
关键词 `JSONL` 被丢掉了，回答自然缺要点。

**根因**：判定器是 LLM，会误判。它按"这条片段能不能单独回答问题"来裁，
而**多跳问题**需要的是"几条片段拼起来"，单看每条都不足以回答 → 被逐条判为不相关。

**修复**：两道保险 ——

```
# ① 分数下限保护：分数接近本批最高分的片段，即使被判"不相关"也保留
ratio = s.agent_score_floor_ratio if grade.sufficient else s.agent_score_floor_ratio_loose
floor = max(scores) * ratio
keep = (str(i) in relevant_ids) or (item.score >= floor and item.score > 0)

# ② 分情况下限：判定"资料不足"时用更宽松的系数（0.25），
#    因为此时本就缺信息，再裁剪只会雪上加霜；判定"充分"时才收紧（0.55）
```

> [key] **过滤可以少留，但不能把高分证据扔掉。** 任何"让模型决定丢弃信息"的环节，
> 都要写一条基于**确定性信号**（这里是精排分数）的安全网。
> 顺带说：这条修复本身也说明了为什么必须有"证据要点覆盖率"这种细粒度指标 ——
> 只看"回答准不准"是发现不了"证据被误杀"的。

### 坑三：结构化输出不守格式 → 节点静默降级

**现象**：日志里出现 `Agent 节点 compress 输出不可用（第 1 次）：输出不是合法 JSON`，
压缩节点连续两次失败后走了兜底（用原文前 N 字截断），效果打折但**流程没崩**。

**根因**：提示词里写的是 `{"items": ["...", "...", ...]}`，
模型有时会**直接返回一个 JSON 数组** `["...", "..."]`，而不是对象。
解析器只接受对象，于是判定为"非法 JSON"。

**修复**：① 解析器兼容数组（自动包一层 `{"items": [...]}`）；
② 提示词显式写"只输出 JSON 对象（不要输出数组）"。

> [tip] 这个坑的价值在于它**没有造成故障**：两次失败 → 走保守兜底 → 用户拿到可用的答案。
> 这正是"结构化输出必须有兜底"的意义。反过来说，如果你在日志里看到大量
> "输出不可用"，那说明提示词或解析器该改了 —— **兜底是安全网，不是常态**。

# 第七部分　指标讲清楚：检索准确率、应答准确率与幻觉率

## 7.1 指标定义与计算口径

| 指标 | 定义 | 计算方式 | 怎么用 |
| --- | --- | --- | --- |
| 检索准确率 Recall@k | 期望文档是否进入前 k 条来源 | 命中题数 / 可答题数 | 低于阈值先查分块与检索参数 |
| 命中率 Hit@1 | 期望文档是否排在第 1 位 | 排第 1 的题数 / 可答题数 | 衡量“第一顺位就可信”的比例 |
| MRR | 平均倒数排名 | mean(1/rank) | 比 Recall 更细，能看出排得靠不靠前 |
| 证据要点覆盖率 | 检索到的正文覆盖了多少回答所需信息 | 命中要点数 / 要点总数 | 期望文档只有一篇时**唯一有区分度**的检索指标 |
| 应答准确率 | 回答正确或正确拒答的比例 | (答对 + 正确拒答) / 已判定 | 端到端效果 |
| 生成层准确率 | 只在“检索到资料”的前提下看生成质量 | 答对 / 有证据的题数 | 把检索问题与生成问题分开定位 |
| 幻觉率 | 编造 + 错误拒答的比例 | (fabricated + false_refusal) / 已判定 | **核心风险指标** |
| 无答案误答率 | 库里没答案却作答的比例 | 误答题数 / 不可答题数 | 幻觉探针题的通过率 |
| 单问成本 / 延迟 | 平均 token 成本与耗时 | 总成本 / 题数；平均毫秒 | Agent 的代价，必须与收益一起汇报 |

| 版本冲突 | 分页参数跨 7 个版本改名 3 次（page→offset→cursor），必须"以最新为准" |
| 长文埋点 | 关键阈值埋在第 6 节中部，前面 5 节全是铺垫 |
| 口语 vs 术语 | 问题说"发上线"、文档写"发布/灰度"；问题说"数据量变少"、文档写"数据量突降告警" |
| 语义干扰 | 3 篇文档都讲"上线"，但只有 1 篇有回滚判据 |
| 中英混排 | 同一主题中英两份文档，配额与有效期表述有差异 |
| 结构化数据 | 答案要从 CSV 里按"服务名 + 可重试 + 时间最新"三条件筛出来 |

实测结果（同一份代码、两条链路）：

| 指标 | 朴素 RAG | Agentic RAG | 怎么读 |
| --- | --- | --- | --- |
| 检索 Recall@4 | **100%** | **100%** | 期望文档都进了证据池 |
| 检索 Hit@1 | 100% | 81.8% | ⚠️ **不要单看这个**，见 7.4 第 4 条 |
| 证据要点覆盖率 | **100%** | **100%** | 检索到的正文都覆盖了回答所需信息 |
| 应答准确率 | **100%** | **100%** | 11 题答对 + 3 道探针题正确拒答 |
| 幻觉率 | **0%** | **0%** | 两组都没有编造 |
| 平均证据条数 | 3.9 条 | **7.8 条** | Agent 多轮累积，证据翻倍 |
| 平均延迟 | 9.3 s | 46.3 s | ≈5 倍 |
| 单问成本 | 0.0015 元 | 0.0125 元 | ≈8.5 倍 |

**这组数据的价值不在"谁赢"，而在于它证明了工程的底线**：即使语料里塞满了
版本冲突、语义干扰、长文埋点、中英混排，系统依然做到 **Recall@4 100%、要点覆盖 100%、
幻觉率 0%**。同时它暴露了一个方法论问题：排序类指标在"多轮累积检索"下会失真
（7.4 第 4 条给了完整分析）。

> [key] **诚实的总结句式**（可以直接背）：
> 「我的系统在这批困难语料上拿到了 Recall@4 100%、要点覆盖 100%、幻觉率 0%；
> Agent 链路把证据量翻了一倍但代价是约 5 倍延迟，所以我保留了链路开关按场景路由。
> 另外我在评测中发现排序指标对多轮检索是失真的，这一点我在文档里写清楚了。」

### ④ 读表要点：这三组数字连起来说明什么

先把结论说清楚，再看数字：**在"小语料 + 干净检索"的基准上，Agentic RAG 并没有把端到端准确率做得更高**
（两边应答准确率都是 100%、幻觉率都是 0%）—— 因为朴素 RAG 的单轮检索已经足够好了。
Agent 的收益出现在另外三个地方：

1. **生成层质量更高（+11.1 个百分点）**：“生成层准确率”只看“检索到资料的那些题答得对不对”。
   Agent 在这一层的优势来自两件事：证据经过判定筛选（噪声更少）、回答被忠实度自检约束过（更贴资料）。
   而全链路准确率被“检索不到就拒答”拉平了 —— 所以**必须把指标拆层看，否则会得出错误结论**。
2. **能力维度而非精度维度**：决策备忘录、推理轨迹、逐节点成本归因、确定性拒答模板，
   这些是朴素 RAG 结构上不具备的（要加就得改代码，而不是改配置）。
3. **可解释性与可审计性**：每一轮检索了什么、判定为什么说不足、校验发现了什么，
   都在轨迹里留痕。出问题时能定位到"是哪一层错了"，而不是只能重跑一遍。

同时必须主动交代代价与不足：

- **延迟与成本**：平均延迟约为朴素链路的数倍、单问成本约数倍（因为多了规划、判定、改写、校验共 7~8 次调用）。
  这是 Agent 的结构性代价，工程上的正解是**按场景路由**（简单问答走朴素链路），而不是无脑全量上 Agent。
- **证据要点覆盖率略低（-1.9 个百分点）**：判定环节会裁掉一部分片段。
  本项目已经加了"分数下限保护 + 分情况下限"两道安全网（见 6.2 坑二），
  但它仍然是**过滤精度与召回之间的取舍**，不是纯赚。
- **无答案误答率 20%（1 例）需要单独解释**：这一例是探针题“DeepSeek 接口每百万 token 的具体报价是多少”，
  Agent 的回答开头明确写了“资料库中没有找到具体报价数字……因此无法回答具体报价是多少”，
  后面补充了资料里与成本相关的定性描述与操作建议。判官把它归到了 correct（因为回答确实说明了资料不足），
  所以“正确拒答率”从 100% 掉到 80%。**从工程视角看这属于"合格的拒答 + 额外提示"，
  但它确实比基线的写法更啰嗦、更容易被误判** —— 这是一个真实的体验取舍，
  也提醒我们：**拒答模板应该干脆短促**，拒答之后不要长篇补充，否则用户会误以为你答了。

> [key] 这组数字最有价值的用法不是"证明 Agent 更强"，而是三个反问：
> ① 我的场景里检索一轮够不够？（够 → 别上 Agent）
> ② 我更需要精度，还是更需要可解释与决策能力？（后者 → 上 Agent）
> ③ 如果上了，成本能降到什么程度？（分档路由 + 提前收束 + 简单场景回退）

## 7.3 怎么读这些数字（面试时最容易讲错的地方）

1. **不要把“指标没提升”讲成失败。** 简单集上基线本来就是满分，诚实的说法是“改造在简单场景下没有回归，在困难场景下带来了 X 个点的提升”。
2. **Agent 的代价要主动说。** 延迟与成本确实上升（多了规划、判定、校验几次调用），换来的是幻觉率下降与过程可解释。工程上正确的做法是**按场景路由**：简单问答走朴素链路，复杂或决策类问题才走 Agent。
3. **区分“检索层问题”与“生成层问题”。** 全链路准确率被“检索不到就拒答”拖低时，看生成层准确率才知道模型本身有没有问题 —— 这就是把指标拆层的目的。
4. **小样本指标不等于生产指标。** 11~30 题的标注集足够看趋势、做回归对比，但不能对外宣称“线上准确率 93%”。这个边界要主动划清。

> [key] 被追问“你怎么量化的”时，按这个顺序回答：① 标注集怎么设计的（三类题 + 幻觉探针）；② 指标口径怎么定的（幻觉率把错误拒答也算进去）；③ 判官怎么保证一致性（强制 JSON + 四分类 + 解析兜底）；④ 结论的边界在哪（小样本、可复现、用于回归对比）。

## 7.4 评测方法本身的四个局限（主动说出来更加分）

1. **判官也是模型，它的判断会有噪声。** 本项目用同一族模型（deepseek-chat）当判官，
   并强制 JSON + 四分类 + 解析兜底来降低方差；但"正确/编造"的边界仍带主观性。
   生产上更稳的做法是：① 关键结论用**人工抽检**复核（抽 10~20 条逐句核对）；
   ② 判官换成更强的模型并只做"是/否"二分类；③ 记录判官的 `unsupported` 字段作为证据留档。
2. **小样本只能看趋势，不能当线上指标。** 11~30 题的标注集用于**回归对比**（改前 vs 改后、
   参数 A vs 参数 B）足够，但不能对外宣称"线上准确率 93%"。
3. **语料一变，指标就不可比。** 期望文档、要点关键词都与具体语料绑定，
   所以评测必须固定语料（本项目评测脚本会在空库时自动灌入 sample_docs + 指定的长文档），
   换了知识库就要重新标注、重新建立基线。
4. **⚠️ 排序类指标（Hit@1 / MRR）对"多轮累积检索"是失真的** —— 这是本项目的实测发现，值得单独讲：

   在困难语料（7 篇文档 / 14 题）上跑双链路对比时出现了这样一组数：

   | 指标 | 朴素 RAG | Agentic RAG | 看起来像 |
   | --- | --- | --- | --- |
   | 检索 Hit@1 | **100%** | **81.8%** | Agent 变差了 |
   | 检索 MRR | 1.000 | 0.879 | Agent 变差了 |
   | 证据要点覆盖 / 应答准确率 / 幻觉率 | 100% / 100% / 0% | **100% / 100% / 0%** | 完全打平 |
   | 平均证据条数 | 3.9 条 | **7.8 条** | Agent 收到两倍证据 |
   | 平均证据字数 | 1639 | **3080** | … |

   结论不是"Agent 变差"，而是**指标口径的局限**：Agent 每轮都会把新检索结果**并入**证据池
   （平均 3 轮 → 7.8 条），而 `rank` 取的是"期望文档在这批证据里的最好名次"，
   证据变多自然会把名次往后挤。落到那两道题上：
   - E1「网关默认超时是多少」：基线证据 1513 字 → Agent 4355 字，**答案依然给出"800 毫秒"**，
     并且额外说明了"早期是 5000、示例里覆盖成 3000、不要混淆"；
   - E6「表里数据量突然变少怎么处理」：Agent 给出"不要重跑 + 40% 阈值 + 标准排障顺序"，
     判官结论是"核心事实均有资料依据"。

   **所以排序指标要这样用**：① 只在**单轮检索**下用它衡量检索质量；
   ② 多轮 Agent 场景要看**"期望文档是否进入证据池"（Recall@k）**、**要点覆盖率**与**答案正确率**；
   ③ 若一定要比"名次"，就要固定证据条数（例如只取 top-4 再算 rank），否则等于拿""
   检索一轮的精度"去比"累积三轮的覆盖"。

> [star] 主动讲出这四条局限（尤其是第 4 条这种"自己指标打自己脸"的发现），比"我的准确率 93%"
> 更能体现工程成熟度 —— 面试官最怕的是"指标很好看但说不清怎么来的"。

## 8.1 三十秒版本

“我把原来的 RAG 问答系统升级成了 Agentic RAG。原来是一条固定流水线：检索一次、重排、生成；现在是带决策的闭环：先规划任务和检索式，检索后让模型判定资料够不够、哪些相关，不够就改写检索式再检一轮；生成前按判定过滤证据，没有证据就直接拒答；生成后再做一次忠实度自检。每一步都以 SSE 事件推给前端，也逐节点记账 token 和成本。用同一套标注集做前后对比，困难场景下检索准确率与幻觉率都有明显改善。”

## 8.2 两分钟版本（按“问题 → 方案 → 证据”展开）

- **问题**：朴素 RAG 有四个失效模式 —— 检索一次定生死、结果不质检、上下文没预算、生成后没校验。
- **方案**：围绕四个失效模式各加一个决策点（规划、相关性判定、证据压缩、忠实度自检），用受控 Agent 编排（决策点交给模型，控制流用代码兜底）。
- **工程**：6 个正交工具用统一 JSON Schema 契约；判定 / 校验 / 压缩三处结构化输出都有重试与保守兜底；决策类问题产出结构化备忘录。
- **证据**：同一标注集两条链路对比、Agent 分层验收脚本 A0~A9、逐节点成本归因。

## 8.3 简历条目参考写法

- 链路改造：把固定 RAG 流水线重构为 Agent 状态机（规划 → 多轮检索 → 相关性判定 → 反思改写 → 生成 → 忠实度自检），关键决策点交给模型、控制流由代码兜底，单进程可跑、不依赖外部编排框架。
- 检索自评与纠错：引入相关性判定节点与强证据提前收束策略，检索不足时自动改写检索式再检，把“召回不足”与“噪声进上下文”两类问题拦在生成之前。
- 防幻觉双闸门：生成前按判定过滤证据、无证据直接短路拒答；生成后做忠实度自检并标注无依据陈述。
- 工具与决策交付：实现检索 / 改写 / 压缩 / 决策备忘录 / 库统计 / 安全计算 6 个工具（统一 Schema 契约），决策类问题自动产出「结论-依据-风险-行动项」结构化备忘录。
- 可观测与可评测：推理轨迹以 SSE 事件流推送前端，逐节点记账 token 与成本；自建双难度评测集（含幻觉探针）与 Agent 分层验收脚本，输出检索准确率 / 应答准确率 / 幻觉率。

# 附录 B　高频追问与答题要点

### Q1. Agentic RAG 和普通 RAG 的本质区别是什么？

控制流从“写死的单向流水线”变成“带决策的闭环”：检索几次、用哪些证据、答不答得出来，都由运行时判断。关键不是多了几次模型调用，而是多了“判断”和“纠错”这两个动作。

### Q2. 为什么不用 LangGraph 之类的编排框架？

本项目用显式状态机（async generator）实现，好处是控制流可读可测、事件能边跑边推给前端、零额外依赖、单进程可跑。框架解决的是“复杂图”问题；本项目是线性带分支的循环，自己写反而更透明。如果状态图确实很复杂，用框架是合理的。

### Q3. 多轮检索怎么保证不会一直循环下去？

三重约束：① 硬上限 `agent_max_retrieval_rounds`（默认 3）；② 强证据提前收束（精排分够高就不再检）；③ 每轮必须产出新检索式（与已用过的去重，避免用同一个问法反复检）。

### Q4. 判定器（grade）和校验器（verify）有什么区别？

判定器看“进去的资料”，决定上下文里放什么（省 token + 去噪）；校验器看“出去的答案”，决定要不要向用户标注风险（保正确性）。一个管入口，一个管出口。

### Q5. 幻觉率怎么定义？为什么把“错误拒答”也算进去？

定义是“答案与事实不符的比例”，三类都算：编造无依据陈述、引用不存在的编号、以及资料够用却拒答。如果不把错误拒答算进去，只要让系统“什么都说不知道”就能把幻觉率刷到 0，指标就失去意义了。

### Q6. Agent 比普通 RAG 慢多少、贵多少？值得吗？

本项目实测延迟约为朴素链路的数倍、单问成本也相应上升（因为多了规划、判定、校验几次调用）。值不值得看场景：简单事实问答走朴素链路更划算，复杂综合与决策类问题才走 Agent —— 所以接口上保留了 agent 开关做按场景路由。

### Q7. 结构化输出失败怎么办？

三层防御：① 重试一次；② 容错解析（去代码围栏、取第一个 JSON 对象）；③ 保守兜底（判定 → 不足、校验 → 放行、压缩 → 原文截断）。核心原则是：**LLM 是概率组件，控制流必须比它更确定**。

### Q8. 怎么证明改造真的有效？

同一套标注集、同一份语料、两条链路各跑一遍（`scripts/eval_agentic.py --mode both`），输出检索准确率 / 应答准确率 / 幻觉率 / 成本延迟的对比表；再加一份 Agent 分层验收（A0~A9）证明链路本身没坏。所有脚本可复现，退出码可接 CI。

### Q9. 如果知识库里真的没有答案，系统表现如何？

两道防线：证据池为空时**不调用模型**，直接返回确定性拒答（说明检索了什么、为什么答不了、建议怎么补充）；即便有证据但不足以回答，判定器会把 sufficient 判为 false，同样走拒答分支。本项目 10 道库外探针题里只有 1 例被判为"作答"（那例其实也明确写了"资料库中没有找到具体报价"，只是拒答后补充了相关线索），其余全部明确拒答且无编造。

### Q10. 这个改造里最容易被忽略的工程细节是什么？

三件事：① **轮数上限与超时**（没有它，延迟和成本失控）；② **逐节点计量**（否则说不清钱花在哪）；③ **评测集里的幻觉探针**（否则会误以为系统已经很好）。前两件决定系统能不能上生产，第三件决定你能不能发现系统其实还不够好。

## D.3 如果脚本报权限错误（PermissionError）

现象：脚本报 `PermissionError: [Errno 13] Permission denied`，但用编辑器/资源管理器手工另存却成功 ——
这说明是**进程权限**问题（Windows 受控目录、企业策略或容器沙箱里都常见），不是代码问题。三种处理方式：

1. **改输出目录**：本项目所有生成脚本都支持 `--out` / `--out-dir` / `--metrics-dir`，
   先写到有写权限的目录，再手工拷回项目即可；
2. **在普通终端里跑**：把命令复制到你自己的 PowerShell / CMD 执行，权限跟着登录用户走；
3. **检查目录安全设置**：确认当前用户对 `docs/`、`data/` 有「修改」权限（属性 → 安全 → 编辑）。

> [tip] 这也是本次改造顺手沉淀的一条工程习惯：**工具脚本不要把输出路径写死**，
> 一律开成参数。换机器、换 CI、遇到权限限制时，改一个参数就能继续跑，而不是改代码。
