# 踩坑记录：`.env` 写了一行"永远不生效"的配置

> 记录日期：2026-10-10　｜　发现场景：用困难语料做检索验收时 CSV 上传被 400 拦掉

## 现象

灌困难语料（`sample_docs/hard/`，7 篇含 `07_线上问题登记表.csv`）时：

```
[FAIL] 07_线上问题登记表.csv → 不支持的文件类型 .csv，仅允许：docx, md, pdf, txt
检索命中：10/11（未命中 1 题）        ← E10 必然未命中，因为它就是查 CSV 的
回答要点覆盖：25/27 = 92.6%
```

但 `parsing.py` **本来就支持 csv**（`_parse_plain` 的扩展名列表里有 `.txt/.md/.csv/.json`…），
配置里也写了允许——问题出在**配置从来没被读到**。

## 根因：字段名与 `.env` 变量名不匹配

`app/config.py` 原代码：

```python
allowed_extensions_raw: str = "pdf,docx,txt,md"     # 字段名带 _raw
```

`.env` / `.env.example`：

```ini
ALLOWED_EXTENSIONS=pdf,docx,txt,md                  # 变量名不带 _raw
```

而 **pydantic-settings 是按「字段名」映射环境变量的**（大小写不敏感，但没有隐式别名）。
所以它去找的是 `ALLOWED_EXTENSIONS_RAW`，而 `.env` 里写的是 `ALLOWED_EXTENSIONS`：

- 该行被**静默忽略**（`extra="ignore"`，不报错、不警告）；
- 程序一直使用代码默认值 `"pdf,docx,txt,md"`；
- 因为两个值恰好都是 `pdf,docx,txt,md`，**肉眼完全看不出问题**——直到需要 csv 时才暴露。

验证方式（一行即可复现）：

```powershell
.venv-rag\Scripts\python.exe -c "import sys; sys.path.insert(0,'.'); from app.config import Settings, ROOT_DIR; s=Settings(); print(repr(s.allowed_extensions_str)); print([l for l in (ROOT_DIR/'.env').read_text(encoding='utf-8').splitlines() if 'ALLOWED' in l])"
```

输出会显示：**文件里是带 csv 的新值，而 Settings 读到的是旧值。**

## 修复

字段改名，去掉 `_raw` 后缀，让 `.env` 用最自然的写法（`app/config.py`）：

```python
allowed_extensions_str: str = "pdf,docx,txt,md,csv"   # 字符串形式，由 property 解析成集合

@property
def allowed_extensions(self) -> set[str]:
    return {s.strip().lower() for s in self.allowed_extensions_str.split(",") if s.strip()}
```

并顺手把 csv 加进默认值（与 `parsing.py` 的能力对齐），`.env` / `.env.example` 同步为：

```ini
ALLOWED_EXTENSIONS=pdf,docx,txt,md,csv
```

## 修复后复验（真实 HTTP 链路）

```
[OK] 07_线上问题登记表.csv → 2 chunks
检索命中：11/11（全部命中，且期望文档均排第 1 位）
回答要点覆盖：26/27 = 96.3%
库外探针正确拒答：3/3（全部正确拒答）
```

## 同一坑的第二个受害者：说明文档被当成语料

`seed_hard_corpus.py` 原来只排除 `README` 与 `test_cases.json`，
而说明文件名是 `_说明_怎么用这批困难语料.txt`（下划线开头，不是 `_readme`），
于是它被上传入库，成为**干扰文档**：

- 它的正文里写了"预期基线/判定标准"，等于把答案送进了上下文；
- 实测 E5/E7 的 top-3 被它占位，**E7 从第 1 位掉到第 2 位**。

已修：排除规则改为「`_` 开头 / `test_cases` / `readme` / `说明` 开头一律不灌」，
并提供 `--include-docs` 用于**故意**模拟"整个文档目录直接上传"的场景。

## 两条可以带走的经验

1. **pydantic-settings 的字段名就是环境变量名**。凡是"存字符串、用 property 解析"的字段，
   命名要么与 `.env` 完全一致，要么在 `.env.example` 里把 `_RAW` 后缀写清楚
   （本项目另一处 `llm_task_routes_raw` 就是靠 `.env` 里写 `LLM_TASK_ROUTES_RAW` 才生效的）。
2. **配置类问题不会报错，只会"用默认值"**。所以要么加一条启动自检
   （把关键配置打印出来：允许扩展名、分块大小、Agent 轮数），要么在 CI 里断言
   "`.env` 里的每个键都能在 `Settings.model_fields` 里找到同名/别名"。
   后者是个很便宜的回归防线，值得加。

## 顺带建议：加一条配置自检（可选）

```python
# scripts/check_env.py —— 校验 .env 里的键是否都能被 Settings 识别
import sys, pathlib
sys.path.insert(0, ".")
from app.config import Settings, ROOT_DIR

fields = {f.upper() for f in Settings.model_fields}
alias = {(fi.alias or "").upper() for fi in Settings.model_fields.values()}
known = fields | alias
bad = []
for line in (ROOT_DIR / ".env").read_text(encoding="utf-8").splitlines():
    line = line.strip()
    if line and not line.startswith("#") and "=" in line:
        key = line.split("=", 1)[0].strip().upper()
        if key not in known:
            bad.append(key)
print("无法识别的配置项：", bad or "无")
sys.exit(1 if bad else 0)
```
